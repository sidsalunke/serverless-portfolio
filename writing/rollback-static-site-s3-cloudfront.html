Automatic rollback for a static S3 + CloudFront site

This site restores its previous version when live tests fail after a deploy. For three and a half months that rollback could not run, because of one line of GitHub Actions configuration. This is how the pipeline works, how the bug hid, and how I fixed and tested it.

By Siddharth Salunke · 11 November 2026

The setup

The site is plain HTML, CSS and JavaScript in a private S3 bucket, served through CloudFront. A merge to master triggers a GitHub Actions workflow that syncs the files to S3, invalidates the CloudFront cache and runs a Playwright suite against the live domain. GitHub authenticates to AWS with a short-lived OIDC token, so there are no stored access keys.

A static site has no deployment slots, no blue/green switch and no traffic splitting. aws s3 sync overwrites the files in place, and from that moment every visitor gets the new version. If the new version is broken, the only fix is to put the old files back. I wanted the pipeline to do that without me.

The design: deploy, verify, restore

The workflow has three jobs that matter here.

1. Deploy, and remember what was live

Before it uploads anything, the deploy job records the commit that is currently live. On a branch where every merge is one commit, that is the parent of the commit being deployed. 

- uses: actions/checkout@v4
  with:
    fetch-depth: 2  # need HEAD and HEAD~1 for rollback

- name: Record pre-deploy commit SHA
  id: prev-sha
  run: echo "sha=$(git rev-parse HEAD~1)" >> $GITHUB_OUTPUT

The job exposes that SHA as an output, so a later job can read it.

2. Wait for the CDN, then test the live site

After the sync, the job creates a CloudFront invalidation and blocks until it completes. 

- name: Wait for CloudFront invalidation to complete
  run: |
    aws cloudfront wait invalidation-completed \
      --distribution-id ${{ secrets.CLOUDFRONT_DISTRIBUTION_ID }} \
      --id ${{ steps.invalidation.outputs.id }}

This step is easy to leave out, and without it the check is meaningless. If the tests start while edge locations still hold the old files, they pass against the previous version and tell you nothing about the one you just shipped.

The e2e-live job then runs the same Playwright suite that runs on pull requests, pointed at the production URL. It covers navigation, SEO markup, accessibility, the security response headers, and that files such as robots.txt and the sitemap are really being served. Some of those can only fail in production. A wrong Content-Type on an image or a file missing from the sync allowlist never shows up against a local server.

3. Restore the previous commit if the tests fail

The rollback job checks out the recorded SHA, runs the same sync commands as the deploy, invalidates the cache again and then exits non-zero, so the workflow shows red. 

rollback:
  needs: [deploy, e2e-live]
  steps:
    - uses: actions/checkout@v4
      with:
        ref: ${{ needs.deploy.outputs.previous-sha }}
    # ...same aws s3 sync steps as the deploy job...
    # ...invalidate CloudFront and wait...
    - name: Fail workflow to signal bad deployment was rolled back
      run: exit 1

Rolling back by redeploying an old commit means the rollback uses the same code path as every normal deploy. There is no second mechanism to maintain.

The bug: the rollback job could never run

I added the rollback on 25 July 2026. The same day, a deploy failed its live tests. The rollback job did not run. GitHub reported it as skipped, and the version that had failed its tests stayed live.

The condition on the job looked correct:

rollback:
  needs: [deploy, e2e-live]
  if: needs.e2e-live.result == 'failure'

The cause is a rule in GitHub Actions that is documented but easy to miss. If a job’s if contains no status function (success(), failure(), always() or cancelled()), GitHub adds success() && to the front of it. success() is false as soon as any job in needs has failed. So the real condition was: 

if: success() && needs.e2e-live.result == 'failure'

Those two halves cannot both be true. The job was skipped in the one situation it was written for. The fix is to state the status function explicitly: 

if: always() && needs.deploy.result == 'success' && needs.e2e-live.result == 'failure'

The check on needs.deploy.result matters once always() is there. Without it, a deploy that failed before uploading anything could still trigger a rollback of files that never changed.

Why nothing caught it

A skipped job is grey, not red. The workflow was already red because the tests had failed, which is what a correct rollback run looks like too. And the failure path almost never ran: nearly every deploy passes its live tests, so the broken job sat unused. The suite tested the site thoroughly and did not test the safety net at all.

I added a unit test that reads the workflow file and asserts that the rollback condition contains a status function. It is a blunt check, but it runs on every pull request and it fails if someone simplifies the line back to the broken form.

Testing the rollback

A fix to a recovery path is not finished until the recovery has been seen to work. There is no staging copy of this site, and the deploy role can only be assumed from master, so the only honest test was a drill in production. I designed it so that a failed drill would cost nothing.

The drill change had two parts:

  • An invisible marker in the homepage, <meta name="rollback-drill">. It changes nothing a visitor can see or use.
  • A test that fails when the live homepage contains the marker. It is skipped unless the suite is pointed at the production URL, so it passed pull-request checks and could be merged.

If the rollback worked, the marker would disappear from production without anyone touching it. If it did not, the worst outcome was a stray meta tag until I reverted the change.

What happened

I merged the drill on 11 November 2026. Times are UTC.

  • 18:39:01 — drill change merged to master.
  • 18:39:34 — marker first seen on the live homepage.
  • 18:39:45 — deploy job finished, CloudFront invalidation complete.
  • 18:41:40 — live tests finished: 161 passed, 1 failed. The failure was the drill test, on all three attempts.
  • 18:41:43 — rollback job started. For the first time, it was not skipped.
  • 18:41:56 — marker gone from the live homepage.
  • 18:42:14 — rollback job finished and marked the workflow as failed, as designed.

The change that failed its tests was live for about two minutes and twenty seconds. Most of that was the test suite running. The rollback itself, from job start to the previous version being served again, took under fifteen seconds for the files and about thirty seconds including the wait for the second invalidation.

One thing I did not expect: while polling the homepage every ten seconds, I twice saw the old version come back briefly after the new one had appeared, once after the invalidation was reported complete. I have not investigated the cause. It did not affect the result, because the live tests retry and the drill test failed on every attempt, but it is a reminder that “invalidation complete” and “every request sees the new version” are not quite the same statement.

Afterwards I reverted the drill change, which removed the marker and the test from the repository, and that deploy passed its live tests normally.

What this does not cover

  • The bad version is live for a few minutes. This is deploy-then-verify, not a canary that exposes a small share of traffic first. Visitors can see the broken version between the sync and the end of the rollback.
  • The repository is not reverted. Production goes back to the previous commit, but master still contains the bad one. The next merge would deploy it again, so a revert or a fix has to follow.
  • It assumes the previous commit was good. HEAD~1 is only the last known-good version if every earlier deploy passed.
  • Infrastructure is out of scope. CloudFront functions, response headers and cache settings are managed with Terraform and are not touched by a rollback.
  • It only catches what the tests check. A regression that the live suite does not look for deploys without complaint.

What I took from it

  • Test the failure path on purpose. A recovery mechanism that has never run is a guess. A harmless marker and a test that fails on it is enough to run the drill safely in production.
  • In GitHub Actions, any job meant to run after a failure needs always() or failure() in its condition.
  • Wait for the CDN invalidation before testing a deploy, or the tests check the old version.
  • Treat a skipped job as a signal. Grey in a pipeline is not the same as green.

The full workflow is in deploy.yml in the site’s repository. The rest of the test pipeline is described on the Quality Suite page.
